1. Project Context
BarrierLens (Project P48) is a four-person team project (PBC, RBM, Parvati, Sharmila) that classifies and predicts barriers Indian women face in accessing healthcare, using NFHS-5 data, and is grounded in Pradhan & De (2025, BMC Health Services Research), which analysed 108,785 women aged 15–49 using multivariate logistic regression and Adjusted Odds Ratios (AOR). BarrierLens extends this with a two-stage ML pipeline (Stage 1: barrier classification with four models; Stage 2: health-outcome impact modelling and K-Means risk clustering), SHAP explainability, and — as the final platform component — an interactive dashboard, chatbot, and policy report generator.
This document addresses ONLY the immediate next milestone: building the interactive BarrierLens dashboard using Stage 1/Stage 2 outputs and selected base-paper visualisations. The chatbot, PDF report generator, and Profile Risk Calculator are out of scope here and are mentioned only as future phases.

2.2 Key Correction Carried Forward Into This Guide
Every recommendation below assumes the INDIVIDUAL-LEVEL pipeline (v5/v2) is the source of truth. District-level assumptions from v4_updated / v1 (proxy-inverted median-split targets, 707-row district features, ~50/50 balanced classes, no SMOTE) are NOT used anywhere in this document. Note also: v467f (companion) and v467i (no drugs) are NOT present in this NFHS-5 individual extract — Household barrier = v467b+c only (permission, money); Facility barrier = v467g+h only (no female provider, no provider). This differs slightly from the base paper's b+c+f / g+h+i grouping and must be labelled as such wherever the dashboard shows a barrier-category comparison against the paper.

14. Final Recommended Dashboard Architecture
RECOMMENDATION: Power BI Desktop, published via 'Publish to Web'
Rationale: the team's outputs are already flat CSVs (Section 10) — Power BI's Power Query ingests these with the least new tooling for a 4-person team on a fixed deadline. Its slicers/drill-through give the interactivity the dashboard's user journey needs with no code. 'Publish to web' gives a free, shareable, website-like embed link for the expo demo without standing up a server.
SHAP plots and any visual Power BI can't natively chart (e.g. SHAP beeswarm) are pre-rendered as PNGs by Member 1/3 in Python and imported as static images into the Explainability page — the one place Power BI's no-code approach needs a Python-produced asset, explicitly scoped to Member 3 in Section 22.
Streamlit + Plotly remains the recommended fallback ONLY if the team is already comfortable in Python and wants full custom SHAP interactivity — not the primary recommendation given its higher build/deployment time for this milestone's timeline.

SHAP PNGs + model_comparison_table.csv → curated explainability asset set (Member 3, with Member 1's inputs)
All summary CSVs + reference CSV + image assets → Power BI data model (Member 1 hands off, Member 3 builds)
Power BI report → interactive dashboard pages (Member 3) → integrated, styled, navigable dashboard (Member 4) → Publish to Web (Member 4)
Throughout, individual-level predictions are converted to dashboard insight strictly by grouped aggregation (mean predicted probability by state / by demographic cell / by cluster) — never by re-fitting or re-deriving new statistics inside the BI tool, so every dashboard number traces back to a specific Stage 1/Stage 2/clustering/SHAP artefact.

30. Final Dashboard Demonstration Flow
Recommended live-demo order, following the analytical journey:
1. National Overview — 'How large is the problem?' (84% observed vs BarrierLens's national predicted rate)
2. Base Paper Comparison — 'How does our pipeline validate the published research?'
3. State-wise Analysis — 'Where is the problem?' (choropleth, toggle barrier types)
4. Demographic Analysis — 'Who is most affected?' (wealth/education/residence panels)
5. Risk Archetypes — 'What distinct risk groups exist?' (named clusters)
6. Stage 2 Outcome Impact — 'What health outcomes are associated with barrier exposure?' (uplift chart)
7. Explainability & Validation — 'Why, and how much should we trust this?' (SHAP + AOR comparison + model metrics)
Total recommended demo time: 8–10 minutes, roughly 60–90 seconds per page, closing on the Explainability page to end on the pipeline's validity evidence.
